# テスト設計 — 仕様とテストのペア配置

**「実装とテストを diff 上で完全に分離し、代わりに仕様とテストを隣に置く」** という配置を採った。
ここはその理由と、Rust / cargo の制約に当てたときに何が起きたかの記録。実ファイルの配線は
[`../lint/check-spec-pairs.sh`](../lint/check-spec-pairs.sh)（規約の機械チェック）と `./run test-*`。

---

## 0. この設計が立っている前提

配置だけ真似ても意味がないので先に書く。**この構成は以下の前提から導かれている。**

- 品質はプラン段階の方針宣言と CI ゲートで担保する。
- **人間の行レビューは最小化し、実装は AI エージェントと CI に任せる。**
- したがって**人間のレビュー面は実装 diff ではなく仕様（＝統合テスト）の diff に置く。**

人間が実装を行レビューする従来型のチームなら、実装とテストが隣接しているほうが実際に正しい。
**前提に同意しないなら、この配置は採るべきではない。**

## 1. なぜ実装とテストを分離するか

Go の `foo.go` / `foo_test.go`、Rust の `#[cfg(test)] mod tests` は、実装とテストを同じ diff に並べる。
これは「レビュー時に振る舞いの変更とその検証を突き合わせられる」という利点があるが、それは
**人間が行単位で diff を読む前提**の利点。上の前提の下では、レビュー対象の行数を膨らませて
本当に見るべき変更を埋もれさせる**ノイズ**にしかならない。

そこで **`src/` にはテストコードを一切置かない**。この規約は `./run spec-check` の [1/4] が
`crates/*/src/` に `#[test]` / `#[cfg(test)]` が現れないことを検査して機械的に強制する。

## 2. Rust のテスト置き場は3つ、うち2つは使えない

| 置き場所                               | 見える範囲       | diff での位置            | 採否                                           |
| -------------------------------------- | ---------------- | ------------------------ | ---------------------------------------------- |
| `src/*.rs` の `#[cfg(test)] mod tests` | private も見える | **実装と同一ファイル**   | ✗ 前提に反する                                 |
| `///` 内の doctest                     | pub のみ         | **実装と同一ファイル**   | ✗ 同上（かつ nextest は doctest を実行しない） |
| **`crates/<crate>/tests/*.rs`**        | **pub API のみ** | 別ファイル・別ビルド単位 | ◎ **既定**                                     |
| `tests-http/`（独立ワークスペース）    | HTTP 越し        | 完全別                   | ◎ 横断仕様                                     |

**`tests/*.rs` は別クレートとしてコンパイルされ、ライブラリを外部依存として link する。**
つまり private が見えず pub API しか触れない ── 「統合テスト＝API レベルの契約」が規律ではなく
**コンパイルエラーで強制される**。Go の内部テスト（`package foo`）と違い、うっかり内部実装に
手を伸ばした統合テストは書けない。

ビルド速度の面でも `tests/` が有利。`#[cfg(test)]` のインラインテストは、テスト時にそのクレートを
**2回**コンパイルする（通常の rlib ＋ `--cfg test` 付きのテストバイナリ）。`tests/` 方式なら lib は
1回で済み、`./run watch` のキャッシュをそのまま使える。

### private をどうしても直接テストしたくなったら

`src` 側に1行だけ置く逃げ道がある（`#[path]` でモジュール本体を `tests/` 側のサブディレクトリに置く）。

```rust
#[cfg(test)] #[path = "../tests/unit/view_comment.rs"] mod tests;
```

ただし現状 lastshot では使っていない。`webcore` の private 関数（view-data コメントの組み立て）は
`render_view` / `render_view_fragment` 経由で pub API から全部叩けたので、**`src` は無変更**で済んだ。
まずは公開 API から叩けないか疑うこと。

## 3. 命名規約 — `spec_` と `unit_`

```
crates/feature-counter/
  src/lib.rs                  ← テストは1行も入らない（tests/ も無い ── §7）
crates/webcore/tests/unit_render_view.rs      ← 純粋ロジック。md 不要
crates/schema/tests/unit_json_contract.rs     ← 同上
tests-http/tests/
  spec_counter.md             ← 仕様（契約の正本。人間が所有・レビューする）
  spec_counter.rs             ← 仕様テスト（md と 1:1）
browser/tests/
  spec_counter.md             ← 同上（ブラウザ層の担当範囲を書く）
  spec_counter.ts             ← Playwright。言語が違うだけで規約は同じ
```

| プレフィックス | 意味                                                               | md ペア  | 誰のものか         |
| -------------- | ------------------------------------------------------------------ | -------- | ------------------ |
| `spec_`        | **仕様テスト**。API レベルの契約。機能追加・修正で必須             | **必須** | 人間（レビュー面） |
| `unit_`        | 純粋ロジックのユニットテスト。**人間が必要と判断したものだけ書く** | 不要     | 実装側             |

### ブラウザ層（Playwright）も同じ規約に乗せる

`browser/tests/` は言語が TypeScript というだけで**扱いは仕様テストと同じ**なので、`spec_<name>.ts` +
`spec_<name>.md` のペアにし、`./run spec-check` の検査対象に入れている。**ここに `unit_` は置かない**
（純粋ロジックのユニットは Rust 側の担当。ブラウザを起動する価値があるものだけを置く）。

Playwright の既定の `testMatch` は `*.spec.ts` / `*.test.ts` だが、**`.spec` という中置きは採らなかった。**
`spec_` プレフィックスと情報が重複するうえ（§3 の `.test.rs` を退けたのと同じ理由）、`spec_counter.spec.ts`
のような二重名になる。代わりに `playwright.config.ts` で `testMatch: '**/spec_*.ts'` に絞っている。

この上書きには**プレフィックスを外したファイルがエラーにならず黙って実行対象から外れる**という副作用が
あるので、`check-spec-pairs.sh` の [4/4] が「`browser/tests/*.ts` は全て `spec_` で始まること」を検査して
塞いでいる（沈黙する失敗をそのままにしない）。

サフィックス `_db` は「**生きた Postgres が要る**」印 ── ただし**現在この印が付いたテストは1本も無い**
（理由と復活手順は §7）。`./run test-unit` は素の `cargo nextest run --workspace` で、除外フィルタは
付けていない。

**なぜプレフィックスで分けるか**: §5 の異常検知（「テストだけ動いて md が動かない = 警告」）は
全テストが仕様とペアである前提に立つ。ユニットテストを混ぜると、それを1行直すたびに CI が
誤検知する。Rust では `tests/spec/counter.rs` のようなサブディレクトリが auto-discovery
されない（cargo が拾うのは `tests/*.rs` と `tests/*/main.rs` だけ）ので、ディレクトリではなく
**ファイル名のプレフィックス**で分けるのが素直。

### `.test.rs` は使えない（実測）

当初は `hoge.md` / `hoge.test.rs` のペアを検討したが、**cargo が受け付けない**。
`tests/hoge.test.rs` を置いて `cargo test` した結果:

```
error: invalid character '.' in crate name: `hoge.test`
error: could not compile `rs-test-probe` (test "hoge.test")
```

cargo は `tests/*.rs` を自動でテストターゲット化するが、ターゲット名をファイル名の stem から取るため
`hoge.test` が不正なクレート名になる。

回避策として `autotests = false` ＋ `[[test]] name = "hoge" path = "tests/hoge.test.rs"` を
Cargo.toml に書けば通る（これも実測で確認済み）。**が、採らなかった。** 仕様を1本足すたびに
Cargo.toml の編集が要り（＝そのクレートが再ビルドされる）、「ペアのファイルを2つ置くだけ」という
規約の軽さと、`ls` レベルで済む CI チェックの単純さが失われるため。

**`.test` という中置きは、Go が「実装の隣に置くから区別が必要」だった命名。** `tests/` に隔離する
Rust では情報が重複している。`spec_counter.md` + `spec_counter.rs` で同名ペアの本質は保たれる
（`.md` を `tests/` に同居させても cargo は無視する ── 実測で確認）。

## 4. 仕様 md に何を書くか

`tests-http/tests/spec_counter.md`（HTTP 層）と `browser/tests/spec_counter.md`（ブラウザ層）が現行の実例で、
雛形も兼ねる。必須要素は4つ:

1. **この層は何をテストしているのか** — 契約を並べる前に、**そのテスト群の担当範囲**を書く。
   「何を検証するか」と対で **「何を検証しないか、それはどこが持っているか」** を必ず書く
   （`browser/tests/spec_counter.md` の担当表が実例）。
2. **用語** — 曖昧語を排除する。ただし**用語集を二重に持たない**。lastshot は
   「型は `.proto` に定義する」が掟なので、**`.proto` に現れる語は proto が正典**とし、
   md では proto に現れない語（「カウント値」「view-data」「フラグメント」等）だけ定義する。
   層をまたいで同じ語を使うときは、**先に定義した md を正典として参照**し再定義しない。
3. **前提条件の明示** — 何が起動している必要があるか。何を前提にしてはいけないか。
4. **契約に ID を振り、境界値を列挙する** — HTTP 層は `C-1` / `C-2` …、ブラウザ層は `B-1` / `B-2` …
   と**層ごとに接頭辞を分け**、テスト関数の doc コメントから同じ ID を参照する。境界値は
   「proto3 JSON は 0 値を省略するので value キーの存在を条件にするな」のように、
   **踏むと静かに壊れる方向**を明記する。

**1 を必須にした理由**: テストが複数層に分かれた時点で、md が契約だけを列挙していると
「なぜこの層にこの契約があるのか」「同じことを別の層でも見ていないか」が読み取れなくなる。
担当範囲を明記すると、**層をまたいだ重複**（同じ不変条件を HTTP でもブラウザでも assert する）と
**層の取り違え**（ブラウザ層に文字列 assert を足す等）が md のレビューだけで見つかる。
Playwright は起動が重いので、ブラウザ層が薄いまま保たれるかどうかは実行時間に直結する。

段階導入として、対応の粒度は**まずファイル単位**だけで運用する。md の節見出しとテスト関数名の
対応チェックは、腐り始めてから足す（最初から ID 振りを厳密にやると書くコストが上がり、
仕様を書くこと自体が億劫になる）。

## 5. diff の形で異常を検知する

**仕様変更 ＝ md ファイルと仕様テストの変更**という不変条件が成り立つので、diff の中身を読まなくても
ファイルツリーの形だけで変更の種別が分類できる。

| diff の形                                              | 意味                                                 |
| ------------------------------------------------------ | ---------------------------------------------------- |
| `spec_*.md` + `spec_*.{rs,ts}` + `src/` が動く         | 仕様変更                                             |
| `src/` だけが動く                                      | リファクタリング or バグ修正                         |
| **`spec_*.{rs,ts}` だけ動いて `spec_*.md` が動かない** | **要確認**（バグ修正でテストを黙らせた典型パターン） |

現在 `./run spec-check` が機械化しているのは**ペアの存在**（[2/4] [3/4]）と
**ブラウザ層の命名**（[4/4]）まで。
「md が動かずテストだけ動く」の検出は diff を見る必要があるので未実装 ── PR レビュー時に
`git diff --name-only` の形で目視する運用から始める。

## 6. テストライブラリ — 何を入れて何を入れないか

Rust は**テストハーネスが cargo と標準ライブラリに内蔵**されている（`#[test]` / `assert!` /
`assert_eq!` / `#[should_panic]` / `#[ignore]` / 既定で並列実行 / `-> Result` を返せる）。
JUnit・pytest・jest に相当するフレームワークを選ぶフェーズが存在しない。足すのは**穴を埋める
個別クレートだけ**。

### 現在入れているもの

| クレート                | 何を埋めるか                                                                    |
| ----------------------- | ------------------------------------------------------------------------------- |
| `cargo-nextest`         | ランナー。テストごとに別プロセス。filterset で DB 要否を切り分けられる（§7）    |
| `tokio`（dev-dep）      | `PgPool` 構築が要求するランタイム文脈（`webcore` が `AppState` を組むのに使う） |
| `serde_json`（dev-dep） | 生成型の JSON 表現の検証、view として渡す値の組み立て                           |

外部クレートは**まだ1つも足していない**。`tempfile` すら不要だった（`CARGO_TARGET_TMPDIR` を
cargo が結合テスト向けに用意してくれる）。

### 入れなかったもの（理由つき）

| クレート                        | なぜ入れないか                                                                                                                                                                                                                                |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`insta`（スナップショット）** | **実装の出力から期待値ファイルを自動生成する**道具で、「テストは実装より先に存在する契約」と正面から矛盾する。回帰検知には強力だが、仕様レイヤに混ぜると「テスト＝仕様」の定義が壊れる                                                        |
| **`mockall`**                   | モックだらけで何も検証しないテストを生む。加えて Rust でモックするには trait 抽象が要り、lastshot の具体型設計（生成型をそのまま流す）を壊す                                                                                                  |
| **`#[sqlx::test]`**             | (1) sqlx の `macros` feature が要り、[`decisions/README.md`](./decisions/README.md) #7「`query!` 系マクロは使わない」に抵触 (2) 既定の migration 検出が sqlx 命名 `{version}_{desc}.sql` 前提で、Flyway の `V{ts}__{desc}.sql` と噛み合わない |
| **`rstest`（パラメタライズ）**  | 有用そうだが**まだ必要になっていない**。境界値の列挙が増えて `#[case]` が欲しくなった時点で入れる（今入れても空振り）                                                                                                                         |
| **`pretty_assertions`**         | 同上。HTML 文字列の差分が読みにくくなってから入れる                                                                                                                                                                                           |

## 7. DB テストは現在置いていない — 外した理由と、戻すときの手順

一度 `crates/feature-counter/tests/unit_service_db.rs`（`get_count` / `increment` を実 DB に対して
叩くテスト）を置いたが、**入れた直後に外した**。同じ検討を二度しないよう理由を残す。

1. **検証内容が `tests-http/tests/spec_counter.rs` の真部分集合だった。** 仕様テストは
   HTTP → `rpc` → **同じ `get_count` / `increment`** → 同じ DB を通る。「increment すると増える」
   「読み戻せる」は既にそこで通っていて、ブラウザ E2E も同じ命題を見ている。同じ主張が3層あった。
2. **assert が反証不能だった。** 下の「隔離の問題」から `>=` でしか書けず、`get_count` が誤って
   値を増やすバグを入れても `second >= first` は通る ── **テスト名が主張しているバグを検出できない。**
3. **service 層に検証すべきロジックが無い。** 実体は `select value from counter where id = 1` と
   `update ... returning` の 2 本。測っていたのは実質 Postgres の挙動だった。
4. **CI 時間の節約はゼロなのに機構だけ増えていた。** 実測（run 30162520281）で `Unit tests (DB)`
   ステップは **0s**（postgres サービスも Flyway の 10s もアプリ起動に元から要る）。対して
   `_db` 規約・`test-unit` の除外フィルタ・`test-db`・CI 1ステップ・`[dev-dependencies]` が
   この 1 ファイルのために生えていた。**機構のほうがテストより重い。**

**戻すとき**（service 層にトランザクション・競合処理・集計など実ロジックが入ったとき）:

1. `crates/<crate>/tests/unit_<name>_db.rs` を置く（`_db` サフィックスが「生きた Postgres が要る」印）。
2. `./run` の `test-unit` に `-E 'not binary(/_db$/)'` を戻し、`test-db`（`-E 'binary(/_db$/)'`）を復活させる。
3. CI の `Apply migrations` ステップの**直後**に `Unit tests (DB)` を戻す。

> **落とし穴**: nextest の filterset は**1本もマッチしないとエラーで落ちる**
> （`no binary names matched` → **exit 94**。実測）。`_db` テストが 0 本の状態で除外フィルタだけ
> 残すと `test-unit`（＝ CI の `Unit tests (no DB)`）まで赤くなる。**フィルタとテストは必ずセットで**
> 足す・外すこと。

### 隔離の問題 — 戻すときに必ず踏む

`counter` テーブルは 1 行（`id = 1`）しかなく、nextest はテストを並列に走らせる。さらに開発サーバが
起動していればブラウザ操作でも同じ行が動く。よって**「他の誰も触らない」前提が置けない**。

このため `assert_eq!(after, before + 1)` が書けず、「増えている」（単調増加）でしか検証できない
（上の理由2はここから来ている）。`tests-http` 側は今もこの妥協を採っている ── API レベルの契約
としては単調増加で足りるため。

厳密な等値が必要になったときの選択肢（**まだ採っていない**）:

| 案                          | やり方                                                                                                                                           | 代償                                                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------- |
| **A. トランザクション注入** | サービス層の引数を `&PgPool` から `impl Executor<'_, Database = Postgres>` に変え、テストが `BEGIN` したトランザクションを渡して `ROLLBACK` する | `crates/feature-counter/src/lib.rs` のシグネチャと、呼び出し側の `crates/rpc/src/lib.rs` に手が入る。真の隔離が得られ後始末も不要 |
| **B. テストごとに別 DB**    | `lastshot_test_<n>` を作って流す                                                                                                                 | src 無変更で隔離できるが、DB 作成と migration の下準備が要りテストが重くなる                                                      |
| **C. nextest の直列化**     | `test-groups` で DB テストを `max-threads = 1` にする                                                                                            | 実装は軽いが、開発サーバやブラウザからの並行更新は防げない＝**問題を半分しか解かない**                                            |

**A が本命**。ただし「テストのために本番コードのシグネチャを変える」判断なので、厳密な等値が
実際に必要になってから採る（今は単調増加で十分に意味のある検証ができている）。

## 8. 実行方法

```sh
./run spec-check   # 配置規約の検査（src にテストが無い / spec のペアが揃っている / browser の命名）
./run test-unit    # クレート単体テスト（現在すべて DB 不要。数秒。常時回してよい）
./run test-http    # 起動済みサーバへ HTTP 黒箱（仕様テスト。要 ./run dev）
./run browser      # ブラウザ駆動 E2E（仕様テスト。要 ./run dev + ./run browser-setup）
./run test         # 上を全部（test-http → browser の順に逐次）
```

dev ループ中は従来どおり触っているクレートだけ（`cargo nextest run -p <feature>`）。

**配置規約のゲートは `lint` に寄せてある。** `./run lint` の [7/7] が `spec-check` と同じ検査を回すので、
CI では **lint ジョブだけ**が持つ（test ジョブには置かない）。同じ失敗が2ジョブで赤くなると
「どちらを直せばいいのか」が増えるだけなので、ゲートは1か所にする。`./run spec-check` は
lint 全体を待たずに配置だけ見たいとき用の単独入口。

## 9. いつこの設計を見直すか（失敗条件）

「うまくいっている」を印象でなく観測で判定できるよう、**先に**兆候を決めておく。

| 兆候                                                                   | 意味                                                                                                       |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 仕様 md の平均行数が、テストの成長に対して停滞し始める                 | 書かなくなる前兆                                                                                           |
| md が動かず `spec_*.{rs,ts}` だけ動く diff の頻度が上がる              | 同期崩壊の前兆                                                                                             |
| ブラウザ層の契約（`B-*`）が HTTP 層と同じことを見始める                | 層の担当範囲の崩壊。§4 の担当表が機能していない                                                            |
| `.proto` にも md にも定義の無い語が仕様に混入し始める                  | 語彙統制の崩壊                                                                                             |
| エージェントが仕様を読んだ上で実装中に質問してくる回数が減らない       | 仕様の入力品質の不足                                                                                       |
| `tests/*.rs` が増えて `./run test-unit` の**リンク時間**が体感を超える | 1ファイル1バイナリのコスト。`tests/<name>/main.rs` で束ねる形への移行を検討（ただし md との 1:1 が崩れる） |

最後の1つは Rust 固有。**`tests/` 直下のファイル1個が独立したテストバイナリになる**ため、仕様を
細かく割るほどリンク回数が増える。現時点（テストバイナリ 3 本）では計測に値する差が出ていないので、
数が増えてから [`build-speed.md`](./build-speed.md) に実測を足すこと。
