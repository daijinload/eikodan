# 0003. dev profile の「opt 非対称」— 撤回して全クレート opt-level=0 に統一

- **判断**: 撤回（2026-06-15）。`[profile.dev.package."*"] opt-level = 0`
- **根拠**: [`../build-speed.md`](../build-speed.md) ⑤
- **一度は採っていた**ものを実測でひっくり返した例。

## もともとの構成と、その狙い

`fastweb` 初期は **自前クレート = opt-level 0 / 依存 = opt-level 3** の非対称にしていた。
「依存は一度焼けば `target/` に残るので初回だけのコスト。dev でも実行は速くしたい」という理屈。

## なぜ撤回したか

**「初回だけのコスト」が半分しか正しくなかった。** `cargo clean` / 新規 checkout /
deps が変わるブランチ切替 ── **worktree を行き来する開発ではこの節目を何度も踏む**。

実測（lastshot / dev profile / `cargo clean` 後の cold ビルド / sccache バイパス）:

| 設定 | フルビルド (wall) | rustc 合計 CPU | GET / req/sec | p50 |
|---|---|---|---|---|
| 自前=0 / 依存=3（従来） | 24.02s | 249.7s | 47,874 | 1.03ms |
| **自前=0 / 依存=0（採用）** | **13.18s** | 59.6s | 39,685 | 1.25ms |
| 差分 | **-10.8s (-45%)** | **-76%** | -17% | +0.22ms |

- **コスト**: 依存 opt-3 はフルビルドで wall +約11秒・rustc CPU +約190秒（4倍以上の LLVM 仕事）。
- **便益**: dev バイナリの GET / が 17% 速く、p50 が 0.22ms 縮む。
- **だが dev で負荷試験はやらない。** 手元で人がポチポチする頻度では 17% も 0.2ms も体感ゼロ ＝
  **意思決定に使えない数字**。

## 一般化できた教訓

**profile の役割を混同していた。** dev profile の評価軸は**反復速度だけ**でよく、本番の動作速度は
`[profile.release]`（opt-3）と、デプロイ相当を測るなら `release-max`（opt-3 + LTO + cgu=1）が担保する。
dev で動作速度を取りに行こうとしていたこと自体が誤り。**ms 単位の動作速度より秒単位のビルド速度を取る。**

## 同じ理由で撤回したもの: 「依存だけ LLVM 強制」

opt 非対称を捨てた時点で、「cranelift は強い最適化が苦手だから opt-3 の依存だけ LLVM で焼く」という
カーブアウトの前提も崩れた。測ったところ **wall は完全に誤差範囲（warm で ±0.2s 以内）／rustc CPU は約 -10%
／fallback warning 無し**だったので、`[profile.dev.package."*"] codegen-backend = "cranelift"` に統一した。

採った理由は速度ではなく**単純さ**（自前と依存で backend が揃い、カーブアウトの説明が要らない）。
「codegen がボトルネックになる構成」で勝手に効き始める保険も維持できる。

## 注意（この判断に依存している記述）

[`../build-speed.md`](../build-speed.md) の ①〜③ は**撤回前の構成（opt 非対称）で計測した数値**。
リンカ・並列フロントの評価は opt-level に依存しないので結論は引き続き有効だが、**絶対値をそのまま
今日の構成に当てはめない**こと。④ sccache は新構成で再計測済み（同ドキュメント ④ 末尾）。
